# Project Brief & Implementation Plan: "Rails Store" Demo Application

> Based on the [Rails Getting Started Guide](https://guides.rubyonrails.org/getting_started.html).
> A small e-commerce store app used as a reference implementation and onboarding project.

---

## 1. Project Brief

### 1.1 Summary
Build a minimal e-commerce store where visitors can browse products and, when a
product is out of stock, subscribe by email to be notified when it is back in
stock. Authenticated store staff can create, edit, and delete products. The app
demonstrates the core Rails stack end to end: CRUD, validations, associations,
authentication, file uploads, rich text, email notifications, caching, and I18n.

### 1.2 Goals
- A working reference app that exercises the full Rails "happy path."
- Clean separation between **backend** (data, business rules, mailers) and
  **frontend** (views, forms, layout, interaction) so the work parcels out.
- Each work item below is self-contained enough to hand to one person.

### 1.3 Non-Goals
- Payments / checkout / cart.
- Multi-tenant or role hierarchies beyond "authenticated staff vs. public visitor."
- Production hardening (rate limiting, spam protection on subscribe, etc.).

### 1.4 Primary User Stories
- **US-1** As a visitor, I can view a list of products and open a product page.
- **US-2** As a visitor, on an out-of-stock product I can enter my email to be notified.
- **US-3** As a subscriber, I receive an email when the product is back in stock, with a working unsubscribe link.
- **US-4** As staff, I can log in and create / edit / delete products, including a featured image and rich-text description.
- **US-5** As a visitor, I can switch the site language (English / Spanish).

## 2. Domain Model (shared reference — read before starting any ticket)

| Model | Fields | Associations | Rules |
|-------|--------|--------------|-------|
| **Product** | `name:string`, `inventory_count:integer`, rich-text `description`, attached `featured_image` | `has_many :subscribers, dependent: :destroy`, `has_rich_text :description`, `has_one_attached :featured_image` | `name` present; `inventory_count >= 0` |
| **Subscriber** | `email:string`, `product_id:fk`, `unsubscribe_token:string` | `belongs_to :product` | `email` present; unique token generated on create |
| **User** | (generated by auth) | — | password via bcrypt |

**Key business rule:** when a product's `inventory_count` changes from `0` to a
positive number, every subscriber for that product is emailed and then that
product's subscribers are cleared. This is the one cross-cutting rule — call it
out in both backend and frontend tickets.

## 4. Backend Tickets

### BE-1 · App scaffold & database setup
- **Depends on:** —
- **Deliverable:** New Rails app (or feature branch) with database configured, running `bin/rails server` locally, README updated with setup steps.
- **Acceptance:**
  - `bin/rails db:create db:migrate` succeeds.
  - Root route renders a placeholder.
  - CI runs the (empty) test suite green.

### BE-2 · Product model & migration
- **Depends on:** BE-1
- **Deliverable:** `Product` model with `name`, `inventory_count`, Action Text `description`, Active Storage `featured_image`.
- **Acceptance:**
  - Migrations for products, Action Text, and Active Storage are in place.
  - Validations: `name` presence, `inventory_count` numericality `>= 0`.
  - Model unit specs cover valid/invalid cases (no DB where avoidable; use `build`/`build_stubbed`).

### BE-3 · Products CRUD controller & routes
- **Depends on:** BE-2
- **Deliverable:** RESTful `ProductsController` (`index`, `show`, `new`, `create`, `edit`, `update`, `destroy`) with strong params and `set_product` before-action. Routes via `resources :products`.
- **Acceptance:**
  - All seven actions work end to end (verified by request/integration specs).
  - `create`/`update` handle validation failure by re-rendering with errors.
  - `destroy` redirects to index with a flash message.

### BE-4 · Subscriber model & subscribe/unsubscribe endpoints
- **Depends on:** BE-2
- **Deliverable:** `Subscriber` model (email, product ref, unique `unsubscribe_token`), `SubscribersController#create` (nested under product) and `UnsubscribesController#show` (token-based).
- **Acceptance:**
  - Token generated on create and is URL-safe/unique.
  - Subscribe endpoint validates email presence and rejects duplicates gracefully.
  - Unsubscribe link with a valid token removes the subscriber; invalid token 404s.
  - Integration specs (`:clean_db`) create/destroy their own data.

### BE-5 · Back-in-stock notification (mailer + business rule)
- **Depends on:** BE-3, BE-4
- **Deliverable:** `ProductMailer#in_stock`, plus a model concern that triggers notifications when `inventory_count` goes `0 → positive` and then clears the product's subscribers.
- **Acceptance:**
  - Notification fires only on the `0 → positive` transition, not on every save.
  - Each subscriber gets one email containing a working unsubscribe URL.
  - After sending, subscribers for that product are cleared.
  - Mailer specs assert recipients, subject, and unsubscribe link; use `ActionMailer::Base.deliveries` / a delivery matcher.

### BE-6 · Authentication
- **Depends on:** BE-3
- **Deliverable:** Rails 8 built-in authentication (`User`, `SessionsController`, bcrypt). Public actions (`index`, `show`) allow unauthenticated access; write actions require login.
- **Acceptance:**
  - Unauthenticated write requests redirect to login.
  - Login/logout work; session persists across requests.
  - Specs cover authorized vs. unauthorized access to each write action.

### BE-7 · Fragment caching (optional / stretch)
- **Depends on:** BE-3
- **Deliverable:** Fragment cache product show details keyed so it invalidates on product update.
- **Acceptance:** Cache hit on repeat render; edit busts the cache.

## 5. Frontend Tickets

### FE-1 · Application layout & flash messages
- **Depends on:** BE-1
- **Deliverable:** `application.html.erb` with nav (Home, and Login/Logout slot), flash message region, base stylesheet wired through the asset pipeline.
- **Acceptance:**
  - Layout renders on every page; flash notices/alerts display and are dismissible.
  - Login/Logout slot is a placeholder until BE-6 lands (coordinate the partial name up front).

### FE-2 · Product index & show pages
- **Depends on:** BE-3 (can start against stubbed data)
- **Deliverable:** `index.html.erb` (product list, "New product" link gated on auth) and `show.html.erb` (name, image, rich-text description, inventory status, Edit/Delete gated on auth).
- **Acceptance:**
  - Index links to each product; empty state handled.
  - Show renders featured image and rich text; inventory status reads "In stock" vs "Out of stock."
  - Delete uses a confirmation (Hotwire `turbo_confirm`).

### FE-3 · Product form (new / edit) partial
- **Depends on:** BE-2 (fields), pairs with BE-3
- **Deliverable:** Shared `_form.html.erb` used by `new` and `edit`, including rich-text editor for description and file field for featured image; inline validation error display.
- **Acceptance:**
  - Same partial serves create and update.
  - Server-side validation errors render next to the fields.
  - Image upload and rich text round-trip correctly.

### FE-4 · Inventory / subscribe partial
- **Depends on:** BE-4
- **Deliverable:** `_inventory.html.erb` partial: shows stock status when in stock; when out of stock, shows the email subscribe form posting to the nested subscribe endpoint.
- **Acceptance:**
  - Subscribe form validates email client-side (basic) and shows success/error flash.
  - Renders correctly for both in-stock and out-of-stock states.

### FE-5 · Internationalization (I18n)
- **Depends on:** FE-1, FE-2, FE-3
- **Deliverable:** Extract UI strings to locale files (`en`, `es`), add a locale switcher, and scope routes/params by locale.
- **Acceptance:**
  - Switching locale changes all visible UI strings on index/show/form.
  - No hardcoded user-facing strings remain in the covered views.

## 6. Cross-Cutting / Shared Tickets

### SH-1 · Interface contracts (do this first, together)
- Agree on: route names/paths, the login/logout partial name (FE-1 ↔ BE-6),
  the inventory partial's expected locals (FE-4 ↔ BE-4), and I18n key naming
  convention (FE-5). Capture in this doc so frontend can build against stubs
  before backend lands.

### SH-2 · Test strategy
- Unit specs: models, mailers (no DB where possible).
- Integration specs (`:clean_db`): controllers/endpoints touching the DB.
- Feature specs (Capybara): US-1 through US-5 as smoke tests only.
- Follow the repo's RSpec + FactoryBot conventions.
